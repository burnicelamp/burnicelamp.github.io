# BURNLAMP 问题、处置与经验清单

更新日期：2026-09-16

本清单来自三类可核对证据：本次对话的实际命令与错误、当前工作区保留的审计／发布产物，以及仓库从 2026-09-03 起的提交记录和 `docs/REGRESSION.md`。当前可用的跨对话记忆注册中没有更早的 BURNLAMP 详细对话全文，因此本文档不声称覆盖无法读取的聊天内容。

状态含义：

- **已解决**：当时问题已处理，有验证结果。
- **已降级**：功能可用，但环境或第三方限制仍在。
- **长期约束**：每次修改都需要继续遵守。
- **未完全覆盖**：尚未获得实体设备、凭证或第三方保证。

## A. 仓库、Git 与发布

### A1. GitHub 压缩包快照不是 Git 工作树

- **现象**：初始源码是公开 `main` 的打包快照，目录中没有 `.git`。`git status`、分支、diff 和普通 push 都不可用。
- **风险**：容易把快照误当为已同步仓库，也无法用 Git 自动识别本次变更。
- **处置**：当时以完整快照做本地实现和回归，发布前另行获取远端 SHA 和 tree。
- **以后**：优先用真实 clone/worktree；无 `.git` 时必须在开工记录中明示。
- **状态**：长期约束。

### A2. 该 Codex Windows Git 运行时在 clone 阶段异常中止

- **现象**：使用运行时自带 Git 执行 HTTPS clone 时异常终止。`git-remote-http.exe` 和 `git-remote-https.exe` 位于 `mingw64\bin`，但 Git 在 `mingw64\libexec\git-core` 查找 helper。
- **尝试**：把两个 helper 复制到 Git 的 `libexec\git-core`，解决了一层路径问题，但 clone 仍不稳定，不适合在该任务中继续反复重试。
- **处置**：改用 GitHub Git Data API 创建 blobs、tree、commit 并非强制更新 `main`。
- **以后**：先用系统 Git；出现同样 helper 症状时不要把时间耗在无限 clone 上。API 只是有授权的发布降级。
- **状态**：已降级；运行时故障未在项目内根治。

### A3. GitHub CLI 不可用

- **现象**：环境中没有可用的 `gh` 命令。
- **影响**：不能直接使用 `gh auth`、`gh api` 或 `gh run watch`。
- **处置**：认证使用 Git Credential Manager，GitHub 读写使用 HTTPS API，Pages 状态使用 GitHub 页面／API 核对。
- **状态**：环境约束。

### A4. 初始没有已保存的 GitHub 凭据

- **现象**：已确认无可用的 GitHub 凭据，因此不能在未授权状态下写入用户仓库。
- **正确行为**：不声称已发布，不尝试绕过认证；在用户要求发布后通过 Git Credential Manager 打开 GitHub 互动登录。
- **验证**：写入前确认登录账号为 `burnicelamp`，并确认对 `burnicelamp/burnicelamp.github.io` 具有 push 权限。
- **状态**：已解决于当次发布；新环境不应假设认证仍存在。

### A5. 临时凭据必须可验证地清除

- **现象**：为 API 发布使用了临时 DPAPI 凭据存储。
- **处置**：发布后清空进程中的 Authorization 和密码变量，移除环境变量，并删除临时存储目录；结果验证为目录不存在。
- **以后**：凭据不写入仓库、文档、日志或交付压缩包；不在最终答复输出 token。
- **状态**：已解决，长期安全约束。

### A6. 临时 API 发布脚本硬编码了 19 个文件

- **现象**：当次 `work/publish-github.ps1` 只上传指定的 19 个变更文件，提交信息也固定为当轮文字。
- **风险**：后续原样运行会漏交新文件，或产生错误提交说明。
- **以后**：优先正常 Git；如必须用 API，根据当次已审核 diff 生成明确清单，并在创建 commit 前再比较远端基线 SHA。
- **状态**：已识别；旧脚本不可复用。

### A7. 发布成功不等于正式站已通过验收

- **现象**：GitHub Pages 可以成功构建和部署，但自定义域名、CDN 缓存、外部图片和浏览器行为仍需单独验证。
- **处置**：本轮提交 `fa5b6daad573c09aef31a00fe11637c2d88254d7` 的 Pages 任务成功后，又对正式域名运行了 1440×1000 和 390×844 交互审计。
- **结果**：新 CSS、设计宗旨、影视切图／选片、图书深链接／目录均已确认，关键请求和控制台无错误。
- **状态**：已解决，长期流程约束。

### A8. 验收文档可能在后续发布后变得过时

- **现象**：`docs/REGRESSION.md` 和本地 `verification.md` 最初写明“未发布”，但后续用户又明确要求发布。
- **风险**：历史时点和当前状态混为一谈。
- **以后**：回归记录保留当时本地结论，另增有日期、SHA 和正式站证据的“后续发布”小节，不悄悄改写历史。
- **状态**：已识别；本次文档更新处理。

## B. Windows、网络与浏览器验收

### B1. PowerShell / curl 的 Windows Schannel 在正式域名上报凭据错误

- **现象**：`Invoke-WebRequest` 报“Authentication failed”；`curl.exe` 报 `SEC_E_NO_CREDENTIALS (0x8009030e)`。这不是站点需要登录，而是当前 Windows Schannel 执行环境的 TLS/凭据问题。
- **对照**：同一时间 Node `fetch` 请求正式域名返回 200，服务器为 GitHub Pages；DNS 正确 CNAME 到 `burnicelamp.github.io`。
- **以后**：不用单一 Schannel 客户端的失败判定正式站离线；用 Node/Playwright 和 DNS 交叉验证。
- **状态**：已降级；环境问题仍可复现。

### B2. 无头 Edge 在默认沙箱中访问正式站超时

- **现象**：Playwright `page.goto` 对正式域名超过 45 秒，后续明确报 `net::ERR_TIMED_OUT`。
- **对照**：Node `fetch` 正常，说明不是 Pages 本身不可达。
- **处置**：在用户批准后于沙箱外运行无头浏览器，线上验收通过。
- **以后**：先用轻量 Node 请求判断站点状态；只有浏览器沙箱超时时，把它当作环境问题申请必要权限。
- **状态**：已降级。

### B3. Playwright 默认临时目录不可写

- **现象**：浏览器启动时因 Windows 默认 temp 路径权限发生 `EPERM`。首次设置的相对 temp 路径又指向了不存在的上级目录。
- **处置**：确认工作区内 `tmp` 存在，再把 `TEMP` 和 `TMP` 设为 `(Resolve-Path '.\tmp').Path`。
- **以后**：不手写未验证的临时目录；使用 `Resolve-Path` 或先创建后设置。
- **状态**：已解决。

### B4. Playwright 模块和浏览器二进制不一定在默认位置

- **现象**：项目目录未必有完整 `node_modules`；Codex 运行时有 Playwright 模块，但声明的 Chromium/Firefox/WebKit 路径未必存在。
- **处置**：通过 `PLAYWRIGHT_MODULE` 指向可用模块，并使用系统 Edge `channel: "msedge"`。
- **以后**：启动前检查模块和 executable，不因 `executablePath()` 返回字符串就假定文件存在。
- **状态**：已降级。

### B5. `DOMContentLoaded` / `load` 不适合做唯一的正式站就绪信号

- **现象**：正式站的关键组件已渲染且可操作，但托管浏览器中 `page.goto(..., waitUntil: "domcontentloaded")` 仍超时。外部嵌入／资源可能长时间保持导航正在加载。
- **处置**：导航只等 `commit`，随后等待项目自己的 `document.documentElement.dataset.contentReady === "true"` 和关键图片实际解码。
- **额外细节**：在页面刚 commit 时 `document.documentElement` 短暂可为 `null`，等待函数需使用可选链或显式空值判断。
- **状态**：已解决，长期验收约束。

### B6. Node 可用但 `npm` 未必进入 PATH

- **现象**：本次 Codex PowerShell 可直接运行 Node v24，但 `npm` 命令报“无法识别”。
- **影响**：`package.json` 的统一 scripts 在正常开发环境中可用，但当前运行时不能假设 `npm` 在 PATH。
- **处置**：文档同时给出 `node tools/...` 和 `node tests/...` 等价命令。需安装依赖时，再定位完整 Node/npm 运行时或由用户授权安装。
- **状态**：已降级。

### B7. 持续加载状态会吞掉自动化的第一次 Escape

- **现象**：线上审计在目录空搜索中按 Escape 时，托管 Edge 把该按键用于“停止尚未完成的页面加载”，弹层因此未关闭。
- **对照**：同一版本的本地浏览器回归已在完整加载状态下验证 Escape 关闭与焦点归还。
- **处置**：正式站审计改用可见关闭控件验证已部署 UI；键盘行为由本地完整加载回归覆盖。
- **以后**：区分浏览器级“停止加载”与 DOM dialog 的 `cancel` 事件，不把测试环境假阳性当作产品回归。
- **状态**：已分析，无产品修改必要。

## C. 影视板块遇到的问题

### C1. 主画面与大量文字、控件叠放

- **原问题**：片名、简介、短评、资料、复制链接和来源占用影像，并用重暗蒙层托字。
- **影响**：影像失去主角地位，不同图片的色彩与构图被统一压暗。
- **处置**：主画面只放真实画面；标题与必要信息移到独立信息区，详情和来源收入低调入口。
- **状态**：已解决。

### C2. 竖版海报与手机窄竖容器破坏银幕感

- **原问题**：图片比例不统一，手机上横图可能被处理成窄竖幅。
- **处置**：四部作品共 12 张真实横版图，统一 16:9 画框，实际解码宽度 1920—3840px。手机继续保持横向比例，不拉伸、不用模糊背景补边。
- **注意**：TMDB URL 扩展名可为 `.jpg`，当次 CDN 根据请求返回 `image/webp`；质量验证以浏览器解码尺寸为准。
- **状态**：已解决，外部托管边界仍在。

### C3. 片内换图和跨作品切换的导航语义混杂

- **原问题**：`01/02/03` 方框、箭头、下拉框、右侧窄条预览同时出现，同一任务有多套控件。
- **处置**：分成三层：画面外的精简图集进度、显示目标片名的上一部／下一部、一个收敛的片目入口。
- **触屏规则**：一次滑动只换同一作品的画面，不同时跨作品；纵向手势留给页面滚动。
- **状态**：已解决。

### C4. 切图可能白闪、黑闪、回跳或图文错配

- **原因**：先清空旧节点再加载新图，或让多次快速操作各自完成不可取消的异步流程。
- **处置**：保留旧画面，新图完成加载与 `decode()` 后再真正交叉淡入；用当前请求标识保证最新操作获胜，取消旧动画和过期回调。
- **验证**：延迟、失败、重试、快速连点、反向切换、直接选片与减少动态均有回归。
- **状态**：已解决。

### C5. 预加载过多会浪费手机流量

- **问题**：一次下载所有高清图固然简单，但 12 张 1920—3840px 图片会无差别消耗流量和内存。
- **处置**：只预加载当前作品的相邻图与必要的下一部首图。
- **状态**：已解决，长期性能约束。

### C6. 外部图片可达性与永久性不是一回事

- **现状**：12/12 TMDB 图片在本轮验证中均返回 200 并正常解码。
- **限制**：这不保证第三方永久托管、各地区网络都可达，也不把外链变成本站的再分发权。
- **降级**：慢网和失败时保留当前画面，显示清晰重试反馈；来源放在详情区。
- **状态**：已降级。

## D. 图书板块遇到的问题

### D1. 彩色作者书签不可扩展

- **原问题**：作者书签横向铺在书顶，作者增加后主页会出现成排标签、遮挡和水平延伸。
- **处置**：移除彩色书签，在书体外放固定的“作者与书目”入口；桌面用目录面板，手机用全屏目录。
- **验证**：用 100 位作者的内存夹具验证主页布局稳定，夹具未进入正式内容。
- **状态**：已解决。

### D2. “点作者就跳第一本”无法浏览该作者全部作品

- **原问题**：作者入口同时承担筛选和选书，用户无法先展开查看作者的作品列表。
- **处置**：目录按作者分组；作者 summary 只展开，不改变当前书；用户再选具体作品。
- **状态**：已解决。

### D3. 搜索、书目下拉和作者入口重复

- **原问题**：同一个“找书”任务有多套控件，主页日常阅读也被管理工具占据。
- **处置**：整合到一个目录，同时搜索作者／书名、显示当前作品、空结果和“返回全部”。
- **状态**：已解决。

### D4. 桌面跨页强行缩小到手机

- **原问题**：桌面书体在手机上继续保留双页或固定高度，导致文字太小、裁切、内层滚动和操作负担。
- **处置**：桌面保留左书名页／右阅读页；手机改为自然单页文档流，不限正文高度，不套正文滚动容器。
- **状态**：已解决。

### D5. 两页重复简介，大号首字占据空间

- **原问题**：书体两侧重复同一段内容，缺乏语义的单字放大作为装饰，书名、作者、年份、摘句和编辑文字层级混乱。
- **处置**：左页只承担作品身份，右页承担摘句、简介和阅读线索；用序号、完整书名和节制的排版取代无意义的大首字。
- **状态**：已解决。

### D6. 长正文、长标题和无摘句易被固定高度裁切

- **处置**：取消依赖裁切的对齐策略，让书页按真实内容生长；没有 quote 时不生成空块。
- **验证**：长标题、长作者名、长正文、无摘句、首尾书目均有回归，无正文裁切和嵌套滚动。
- **状态**：已解决。

### D7. “换一本”和“翻当前书的页”容易混淆

- **问题**：旧数据仍保留部分 `pages` 字段作历史参考，而当前展示不应再用空白纸片假翻页。
- **处置**：当前书页将每个书目入口视为一个可自然阅读的展开面，底部明确显示上一项／下一项的目标标题，不伪造书内翻页。
- **以后**：如真正引入书内多页，必须给它独立状态、标签、深链接和内容对应的翻页动效。
- **状态**：已解决，数据兼容约束仍在。

### D8. 书目混合作品和文献集合，计数不能一律称“本”

- **处置**：主界面和目录使用“个书目入口”或“项”，按作者显示入口数，不暗示每个条目都是独立出版物。
- **状态**：已解决。

## E. 共用代码、动效与文档问题

### E1. 历史 CSS 规则与新组件反复覆盖

- **原问题**：若继续把新规则追加到大样式表末尾，银幕／书页的旧选择器会和新选择器形成难以追踪的优先级链。
- **处置**：新根类收敛为 `cinema-room` / `reading-room`，相关规则集中到 `cinema-books.css`，避免和 `styles.css` 的历史组件规则互相补丁。
- **状态**：已解决，长期维护约束。

### E2. 把放慢、弹跳、强缩放或持续动画误当“精致”

- **早期风险**：网站同时有空间进场、材质倾斜、照片转场和内容切换，很容易叠加成持续运动。
- **处置**：动效只服务状态交接和物件重量；进场只运行一次，指针倾斜有上限且在触屏／失焦／弹层时复位，无持续渲染循环。
- **状态**：已解决，见 `docs/MOTION.md`。

### E3. 动效与 `prefers-reduced-motion` 可以在运行中变化

- **问题**：只在页面启动时读一次减少动态偏好，会使已经运行的动画不能及时停止。
- **处置**：监听 media query 变化，立即取消正在运行的非必要动画，并保留最终可操作状态。
- **状态**：已解决。

### E4. 弹层、深链接和浏览器历史相互影响

- **问题**：选片、选书、详情和照片放大机均可修改 URL；如果弹层只直接 `close()`，Back/Forward 和焦点可能不一致。
- **处置**：`showLayer` 为每个弹层拥有一个 history entry，`leaveLayer` 先退历史再执行后续导航；关闭后归还原始焦点和滚动位置。
- **状态**：已解决，任何新弹层都必须沿用该契约。

### E5. 内容索引可以与 JSON 源失同步

- **问题**：编辑 `content/*.json` 后如果忘记重建索引，搜索、关联和统计会丢内容或留旧条目。
- **处置**：把 `build:content` 放到 `npm run check` 第一步；生成文件不手改。
- **状态**：流程已收敛。

### E6. 压力测试内容不能进入正式数据

- **风险**：80 本书、100 位作者、长正文、无摘句、失败图片等对布局很有价值，但不是用户的正式内容。
- **处置**：Playwright 通过路由或内存注入夹具，不写入 `content/`；审阅截图优先使用真实内容。
- **状态**：已解决，长期内容完整性约束。

### E7. 内容指南会被实现演进甩在后面

- **现象**：银幕／书页重构完成后，`CONTENT-GUIDE.md` 仍描述竖版海报、作者书签、书内分页和旧统计方式。
- **风险**：新对话会忠实地照旧文档实现，把已经解决的问题重新带回站点。
- **处置**：本次同步更新内容指南，并将任务后检查文档一致性写入 `AGENTS.md`。
- **状态**：已解决，长期文档约束。

## F. 第三方服务、真实内容与设备边界

### F1. Apple Music iframe 加载不能证明真实播放

- **历史验证**：Apple iframe 等待 15 秒后仍未显示可读播放控件；同时未捕获请求失败。
- **结论**：“iframe 已 load”、“没有 requestfailed”和“可真实播放”是三个不同命题。
- **处置**：官方模式保留官方外链和重载入口，不伪造播放、进度或歌词同步。未使用登录账号或 MusicKit 凭证验证完整订阅曲目。
- **状态**：已降级，第三方能力未完全覆盖。

### F2. 无真实个人内容时不能为了丰富界面而编造

- **历史情况**：早期轮次缺少真实照片、电影、书籍或评价时，只能用明确标识的原创几何夹具验证结构。
- **处置**：正式站展示真实已发布条目；缺失内容显示诚实空状态，不生成虚假评分、经历或阅读状态。
- **状态**：长期约束。

### F3. 媒体来源、技术可用和发布权是三个问题

- **风险**：找到高清图、有官方链接或能够直链访问，都不自动产生本站永久托管和再分发的权利。
- **处置**：作品资料、图片来源、署名、尺寸和 `usage` 分开记录；授权不明时使用外部引用和失败降级，不偷偷下载到仓库。
- **状态**：长期约束。

### F4. 模拟手机视口不等于实体设备验收

- **已覆盖**：Edge 桌面和 Playwright 手机视口／触屏模拟，包括 320、390、768、980、1440px。
- **尚未覆盖**：实体 iPhone Safari、实体 Android 浏览器，以及不同地区网络下的官方播放和外部图片。
- **以后**：手势、视口安全区、Safari dialog/焦点或真实网络是高风险时，在交付中明确说明，必要时由实体设备补验。
- **状态**：未完全覆盖。

## G. 已经固化的预防措施

1. 根目录 `AGENTS.md` 固化设计宗旨、项目事实、验收与发布边界。
2. `docs/CODEX-WORKFLOW.md` 给出统一的预检、实现、回归、截图、录屏、发布和线上复验流程。
3. `npm run preflight` 在开始时一次报告仓库、远端和正式站基本状态。
4. `npm run check` 统一索引生成、内容验证和内容回归。
5. `npm run check:full` 在此基础上增加全部浏览器和动效回归。
6. 影视外部图片有独立真实网络与像素尺寸验证。
7. 测试夹具通过 Playwright 路由／内存注入，不污染正式 `content/`。
8. 发布需要当轮明确授权；发布后必须核对 Pages SHA 并复验正式域名。
